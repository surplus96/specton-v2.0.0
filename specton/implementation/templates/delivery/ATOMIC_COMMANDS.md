# 승인된 원자 명령

`spec/approved-spec.json`의 `spec-v0.8` / `domain-ir-v2`에서 `domain.commands`를 검토한다.
명령이 없는 패키지에서는 이 기능을 노출하지 않는다. 등록·조회 화면이나 테이블 이름만으로
주문·출고·점검 등의 업무 규칙을 추정하지 않는다.

- 전체 기본키로 특정한 대상 2~8개, 변경 2~8회. 대상마다 등록 또는 수정 한 번.
- 입력은 승인 컬럼의 타입·길이·정밀도에 연결한다. 읽기 전용 대상도 잠근다.
- 값은 입력·잠근 행·형식이 정해진 상수, 계산은 정수/고정소수 덧셈·뺄셈만 허용한다.
- 모든 대상을 잠근 뒤 전 조건을 검사하고, 변경·후 조건·응답·중복 요청 기록을 한 거래로 처리한다.
- 중간 오류·조건 위반·DB 제약·잠금 실패 시 전체 롤백한다. 가변 목록·삭제·외부 송신은 지원하지 않는다.

명령 역할과 해당 테이블의 직접 쓰기 역할은 분리해야 한다. 기준 데이터 관리 역할은 별도
관리 권한이며 직접 데이터를 변경할 수 있다. 명령 실행자에게 관리 역할까지 부여하면
해당 관리 권한도 갖게 된다. 이 계정 부여는 납품 운영자가 검토한다. 행/조직별 소유권 검사는
이 기능의 역할 검사와 별도다.

API는 `Idempotency-Key`가 필요하다. 계정·명령·컴파일된 정책별로 같은 키와 같은 입력은
완료 결과를 다시 반환한다. 다른 입력에 같은 키를 쓰면 충돌한다. 실패한 거래는 키도
저장하지 않아 다시 시도할 수 있다. UI는 동일 입력 재시도에 키를 유지하며, 별도 업무는
`새 요청 작성`으로 시작한다. 브라우저를 닫거나 계정을 바꾼 후의 미확인 요청은 별도
확인이 필요하므로 임의로 새 키를 보내지 않는다.

정책이 바뀌면 중복 기록의 범위도 달라진다. 다른 명령 버전으로 데이터·요청 이력을 이전할 때
기존 키를 새 명령 실행으로 해석하지 않도록 별도 이전·운영 전환 계약이 필요하다.

정상·경계 성공 및 업무 거절 인수 사례는 명세에 명시해야 한다. 사례별 빈 DB에서 실행하는
플랫폼 검증과 실제 고객 환경 업무 인수는 별도다. 단순 화면 렌더 검사를 명령 업무 실행
성공으로 해석하지 않는다. DB 운영 관리자 쓰기나 승인되지 않은 코드의 변경까지 통제하지 않는다.

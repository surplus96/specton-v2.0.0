# 검증 후보 비교와 구현 기준 채택

2026-11-14. 프로젝트 소유자가 생성 후보의 변경과 검증 근거를 검토하고 구현 기준을 채택하는 기능을 구현했다. 다음 확장 단계는 Gmail API 변경 요청 수신과 명세 수정·재검증 연결이다.

## 사용자 흐름

1. **내 프로젝트 → 프로젝트 선택 → 검증 후보 비교·채택**으로 이동한다.
2. 후보와 비교 기준을 고른다. 기본 비교 기준은 현재 채택한 소스이며 최초 채택에서는 빈 기준이다. 같은 프로젝트의 다른 후보를 골라 비교할 수도 있다.
3. 요구사항·역할·엔티티·유스케이스·불변 조건·API·화면·인수 사례·질문 ID의 추가/삭제/수정과 재고 정책·저장/작업 연결 변경을 확인한다. 소스 파일별 변경, 이전/이후 SHA-256과 제한된 텍스트 diff, DDL 변경 여부를 함께 제공한다.
4. 고정 API·브라우저 검사 항목과 연결된 요구/화면/API ID, 보고서 해시를 확인한다. 자연어 업무 인수 조건은 미검증 목록으로 표시한다.
5. 현재 채택 기준과 비교한 적격 후보에 대해 10~2,000자의 사유와 미검증 업무 인수 확인을 입력해 채택한다.
6. 현재 기준과 채택 이력이 갱신된다. 기존 소스·명세·검증 보고서는 보존한다.

채택은 **프로젝트의 구현 소스 기준 선택**이다. 운영 배포·운영 DB DDL 적용·고객 업무 인수 완료를 수행하거나 의미하지 않는다. 과거 소스로 바로 되돌리는 기능은 제공하지 않으며 최신 명세로 생성하고 다시 검증해야 한다.

## 채택 조건과 경합

- Google 세션, 프로젝트 소유권, 변경 요청의 Origin·CSRF 검증을 적용한다.
- 대상은 프로젝트의 최신 설계 기준과 최신 승인 명세 버전·해시에 연결돼야 한다. 승인 산출물의 실제 파일과 출처를 다시 확인한다.
- **가장 최근 검증 작업**이 smoke_passed이고, 브라우저 검사도 통과했으며 리소스 정리가 완료돼야 한다. 이후 대기/실패 작업이 있으면 이전 성공 보고서로 우회할 수 없다.
- ZIP 외부 SHA-256, 내부 파일 manifest, 승인 명세와 템플릿 버전, 보고서 해시와 실행 이미지·검사 코드 해시를 대조한다.
- 비교 해시는 현재 기준, 최신 설계·명세·검증 근거, 파일 변경 및 의미 변경을 결합한다. 채택 시 프로젝트 잠금 아래 다시 계산한다. 기준 ID 또는 비교 해시가 달라지면 409로 거절하고 재비교를 요구한다.
- 프로젝트 잠금으로 채택 순서를 직렬화하고 검증 행 공유 잠금으로 보고서 완료와 경합을 막는다. 사용자 잠금 순서는 미리보기 생성과 일치한다.
- UUID 요청 키와 요청 본문 해시로 재시도를 처리한다. 같은 키·같은 내용은 원래 결과를 반환하며, 이후 다른 기준이 채택됐어도 이력을 새로 만들지 않는다. 같은 키·다른 내용은 409다.
- 이미 같은 소스/검증을 채택했으면 다시 채택하지 않는다. 같은 소스를 새 검증 결과로 재채택할 때에는 별도의 감사 기록을 만든다.

## 저장 구조와 API

스키마 HEAD는 **0007_adoption**이다. 0006의 소스·검증·미리보기 자료를 유지하고 implementation_adoption 테이블만 추가한다. 앱 실행 전 명시적으로 적용한다.

```bash
uv run python -m specton.persistence.migrate upgrade
uv run python -m specton.persistence.migrate check
```

| 경로 (/api/v1/projects/{project_id} 이하) | 기능 |
|---|---|
| GET /candidates | 최근 후보 100개, 최근 검증 상태, 현재 채택 |
| GET /candidates/{candidate_id}/comparison?base_id=… | 같은 프로젝트 후보 비교, 적격 여부와 비교 해시 |
| GET /implementation-baseline | 현재 기준과 최근 이력 50개 |
| POST /adoptions | 검토 근거를 재검증하고 채택 기록 추가 |

POST에는 implementation_id, verification_id, expected_current_id(최초 null), comparison_hash, request_key, rationale, acknowledge_unverified_acceptance=true가 필요하다.

기록은 프로젝트별 순서, 이전 기록 ID·해시, 대상 소스/검증, 검토자·시간·사유·미검증 확인을 포함한다. 현재 기준은 가장 큰 순서의 기록이다. 기존 기록을 수정/삭제하는 API는 없다. 조회 시 기록 해시와 연결을 확인한다. DB 관리자에게도 변경을 막는 외부 서명 감사 저장소는 아니다.

## 비교 제한

비교는 읽기 전용으로 과거 템플릿 바이트 자체를 현재 템플릿과 일치시키지 않는다. 지원하는 ZIP 파일 구성과 명세 계약은 확인한다. 전체 ZIP·압축 해제 합계는 10 MiB로 제한한다. 텍스트 비교는 입력 파일 64 KiB/1,500행 이하, 파일당 8,192자, 전체 65,536자까지만 표시한다. 생략 여부와 전체 파일 해시는 유지한다. 전체 검토에는 소스 다운로드를 사용한다.

고정 브라우저 시나리오의 통과만 채택 조건으로 사용한다. business_acceptance는 not_run을 유지한다. 자연어 인수 조건은 최대 100개를 표시하고 전체 개수도 별도 제공한다. 후보·이력 페이지네이션, 외부 전자서명, 다중 검토자 승인과 운영 릴리스는 후속 범위다.

## 검증

- DB 통합: 초기 채택/재채택, 감사 연결, 재시도, 동시 요청의 200/409 분기, 최신 검증·명세 변경 거절, 소유권/CSRF/확인 입력, 소스/보고서/기록 변조, 0006→0007 근거 보존.
- 단위: 추가/삭제/수정 diff, 출력 상한과 전체 해시 보존, 의미 변경.
- 실제 생성 앱: PostgreSQL·HTTP·Chromium 검증 작업자의 보고서를 받아 비교→채택→조회→재시도까지 실행. [실제 채택 근거](evidence/candidate-adoption-report.json)에 보고서와 비교 해시를 보존한다. 스크린샷 본문은 채택 기록에 복제하지 않는다.
- 플랫폼 UI: tests/browser/candidate-adoption.mjs가 빌드 화면을 실제 Chromium으로 열어 적격/사유/확인 체크의 버튼 제어와 요청 본문·이력 갱신을 확인한다. 이 UI 검사는 API 응답 fixture를 사용하며 실제 Google 로그인 종단 검사와 구분한다.
- CI의 실제 브라우저 검사 단계에도 채택 통합 검사를 추가했다. 원격 CI 성공은 해당 실행 결과로 별도 확인한다.

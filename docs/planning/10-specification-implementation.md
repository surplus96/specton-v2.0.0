# 승인 설계에서 실행 명세 검토·승인까지

2026-11-14, `feat/implementation-foundation`에서 구현했다. [Google·프로젝트 단계](09-google-project-implementation.md) 다음의 명세 작성 흐름이다. 실제 생성 앱 구현이나 Gmail 수집의 완료를 뜻하지 않는다.

> 후속 단계: [기준정보 소스 생성·격리 검증](11-generated-application-implementation.md). 아래 내용과 측정값은 명세 검토 구현 시점의 기록이다.

## 제공하는 동작

1. **내 프로젝트**에서 연결한 승인 기준의 **실행 명세 작성·조회**를 선택한다.
2. 서버가 실제 승인 파일과 기준 버전의 해시를 다시 확인한 뒤 승인 스냅샷의 요구를 가져온다. 같은 기준에는 하나의 명세 이력만 생성한다.
3. **확인 질문**에 답하고 **실행 계약 편집**에서 역할·유스케이스·API·화면·업무 규칙·인수 사례를 보완한다. 초기 화면은 질문 입력과 고급 JSON 편집을 제공한다.
4. **새 버전 저장**으로 계약을 검증하고 새로운 불변 버전을 만든다. 화면에 표시되는 보완 항목은 저장된 버전에 대한 결과다.
5. 질문과 Must 요구의 API·화면·인수 연결 등 계약 검사를 통과한 최신 저장 버전만 **이 버전의 실행 명세 승인**으로 확정한다.
6. 승인 이후에도 보완하여 새 버전을 저장할 수 있다. 이전 승인과 본문은 유지하고, 새 버전에는 다시 승인이 필요하다. 과거 버전은 읽기 전용이다.

현재 초안 생성은 재고(`inventory`) 팩만 허용한다. 설비 등 다른 팩을 재고 템플릿으로 표시하지 않고 거절한다.

초안은 누락 방지를 위해 모든 원본 요구를 `Must`, FR을 화면 필요로 표시한다. 이것은 원본에 없던 업무 결정을 확정한 것이 아니다. 각 요구의 확인 질문에 답해야 하며 우선순위·화면 범위를 바꾸려면 초안과 다른 구체적 사유를 기록해야 한다. API·역할·업무 동작을 임의 생성하지 않는다. `ROLE-unconfirmed`는 승인 불가능한 자리표시자다.

원본 요구와 초기 질문은 삭제할 수 없다. 범위 제외는 요구를 보존한 채 `Won't`와 사유로 표현한다. 사용자가 추가하는 요구는 `origin=user`로 구분한다. 답변만 작성해도 API·화면·인수 계약이 자동 생성되지는 않는다.

## 구현 범위

| 계획 항목 | 이번 결과 | 남은 범위 |
|---|---|---|
| DEV-006 안정 ID·추적 | 프로젝트·원본 실행·요구 ID에서 안정 ID 산출, 명세 객체 종류·출처 유지, 삭제한 최상위 객체 ID 재사용 차단 | 서로 다른 실행의 객체 대응·분할/병합 결정 UI, 필드 수준의 안정 ID 이력, 전체 코드/TC 추적 그래프 |
| DEV-007 실행 계약 | 실제 DB 승인 기준에 SpecBundle을 결합, 출처·계약·준비 검사, 원본 요구의 누락 차단 | 생성기가 지원하는 업무 의미의 컴파일 가능성 검사, 재고 템플릿의 확정/취소 등 세부 정책 |
| DEV-008 명세 보완·승인 | 질문 답변, JSON 계약 편집, 버전 조회, 저장 충돌·stale 승인 차단, 해시·계정에 묶인 승인 | 업무별 구조화 폼, 변경점 비교, 브라우저 자동 인수 확장 |

규칙·API 설명의 업무적 정확성을 코드가 증명하지는 않는다. `ready_for_review`는 명세 계약 검사 통과이고, `approved`는 로그인 사용자가 해당 버전을 승인했다는 기록이다. 생성 앱 기동·검증·배포 상태와 구분한다.

## 버전·동시성·추적 결정

- `spec_document.id`는 한 기준 설계에 속한 명세 이력의 ID다. `SpecBundle.spec_id`와 같다.
- 수정할 때 기존 행을 덮지 않고 `spec_revision`에 새 version/payload/hash/created_by를 저장한다. 부모 해시는 직전 버전을 가리킨다.
- 동일 프로젝트 행을 잠근 뒤 현재 명세 버전과 요청의 `expected_version`·`spec_hash`를 비교한다. 둘 중 하나라도 오래됐으면 409다.
- 수정 요청의 bundle은 조회한 버전의 ID·기준·버전·부모 해시를 그대로 포함해야 한다. 서버가 다음 버전과 부모 해시를 지정한다. 본문이 같으면 새 버전을 만들지 않는다.
- 승인 기록은 `spec_approval`에 대상 명세·버전·해시·인증 사용자 ID를 저장한다. 동일 최신 버전의 승인 재요청은 같은 기록을 반환한다.
- 원본 요구 ID는 UUIDv5로 프로젝트·run·기존 요구 ID에 묶는다. 이름 수정으로 바뀌지 않는다. 다른 run의 `REQ-01`을 같은 객체라고 자동 추정하지 않는다.
- `spec_object`는 명세 이력 안 최상위 객체 ID의 종류·출처와 삭제 버전을 보존한다. 삭제한 ID는 다시 사용할 수 없다. 분할은 새로운 ID를 사용해야 하며 자동 분할/병합 매칭은 제공하지 않는다.
- 생성·저장·승인 시 실제 파일·승인 근거를 재검증한다. 고정한 baseline의 승인 ID·모델 해시·파일 해시와 다르면 422다. 역사 조회는 저장된 명세와 당시 승인 기록을 보여 주며, 파일을 다시 검증했다는 의미가 아니다.

## API

모든 API는 Google 로그인과 프로젝트 소유권을 요구한다. 변경 요청은 정확한 Origin과 CSRF 헤더도 확인한다. 소유하지 않은 대상은 404다.

| 경로 | 결과 |
|---|---|
| `POST /api/v1/baselines/{id}/specs` | 초안 생성 또는 기존 최신 명세 반환 (200, 기준 ID로 중복 방지) |
| `GET /api/v1/specs/{id}` | 최신 bundle, 상태, 준비 검사, 버전 목록, 승인 주체 |
| `GET /api/v1/specs/{id}/versions/{version}` | 과거 버전과 당시 승인 기록 |
| `PATCH /api/v1/specs/{id}` | expected_version, spec_hash, 전체 bundle로 새 버전 저장 |
| `POST /api/v1/specs/{id}/approve` | expected_version, spec_hash에 대한 별도 승인 |

본문의 actor/owner, 알 수 없는 필드, 무효 참조를 거절한다. 신규 응답·입력은 OpenAPI와 프런트 생성 타입에 포함했다. PATCH는 임의 JSON Patch가 아니라 전체 검증 가능한 bundle의 교체 요청이다.

## 실행과 검증

플랫폼 스키마 버전은 `0003_specification`이다. `spec_document`, `spec_revision`, `spec_approval`, `spec_object`를 추가한다. 신규 스키마도 참조 구조와 비교하며 파괴적 downgrade는 지원하지 않는다. 운영 DB에는 자동 적용하지 않았다.

```bash
uv sync --locked
uv run python -m specton.persistence.migrate upgrade
uv run python -m specton.persistence.migrate check
```

Google 실로그인 설정은 이전 구현 기록을 따른다. 이번 검사는 독립 PostgreSQL에서 실제 설계 승인 파이프라인을 사용하며, 외부 LLM과 Google 코드 교환만 고정 응답으로 대체한다. 합성 실행 명세는 API·화면 계약 연결을 검사하기 위한 입력으로, 실제 생성 앱이 구현됐다는 증거가 아니다.

검증 결과:

- Python 전체 회귀: **2,185 통과**, 17 skip, DB·LLM 388 deselected (193.63초).
- PostgreSQL 전체 회귀: **367 통과**, 2,223 deselected (571.82초). 마지막 재고 팩 제한을 추가한 뒤 명세 흐름·이전 집중 검사 **8건**도 모두 통과했다. 집중 검사의 기존 4개 시나리오는 전체 회귀와 중복된다.
- 프런트엔드: **273 통과**, ESLint·OpenAPI 생성 타입 일치·TypeScript/Vite 빌드 통과.
- Ruff·포맷, mypy 143개 소스, 팩 생성 일치 검사 통과.
- 독립 PostgreSQL에서 `0003_specification` upgrade/check 통과. 기존 `0002_identity`의 계정·프로젝트 보존과 신규 표 FK/RLS 변조 거절을 추가 검사했다.

이번 작업 전용 임시 PostgreSQL만 생성·정리했으며 원본 프로젝트와 운영 DB는 변경하지 않았다. 실제 Google OAuth·브라우저 수동 인수·생성 앱 구동·Gmail·운영 배포는 수행하지 않았다.

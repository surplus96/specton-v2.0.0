# 코드 품질과 최적화 계획

## 개선 원칙

동작과 승인 근거를 보존하며 측정된 문제부터 개선한다. 파일 길이만으로 재작성하지 않고, 변경 이유·전후 비교·실패 복구가 있는 작은 작업으로 나눈다. 아래 수치는 현재 성능 실측값이 아닌 후속 작업의 목표다.

## 측정 설계

기준 입력을 작은 20개·중간 200개·상한 1,000개 원문 블록으로 고정한다. 유효한 업무 데이터 모델을 포함하고 원문·정답·팩·프롬프트·환경·코드 해시를 기록한다. 일부 모듈만 시험하는 입력과 전체 인수 입력을 분리한다.

- 결정론 경로: 워밍업 후 30회, p50·p95·최대·실패 수·peak RSS를 기록한다.
- 실제 LLM 경로: 같은 조건 5회부터 시작하고 출력 토큰·재요청·품질과 함께 관측한다. 표본이 작으면 통계적 우위를 주장하지 않는다.
- API 부하: 2개 설계 실행과 20개 조회 연결을 시작 조건으로 정하고, 응답 시간·연결 풀 대기·SSE 조회량을 측정한다.
- 화면: 같은 머신·브라우저·데이터로 번들 크기, 첫 표시, 이벤트 10,000건 누적 후 힙과 재연결 동작을 측정한다.

| 항목 | 초기 목표 | 판정 조건 |
|---|---|---|
| 비LLM 설계 처리 | 기준선 대비 p95 20% 이상 개선 후보 | 동작·추적·해시가 같고 품질 저하 없음 |
| 팩 로딩 | 중간 입력 전체 시간의 유의미한 비중이면 개선 | 캐시 miss·hit와 무결성 재검사 비용 각각 공개 |
| 상태·목록 API | 위 기준 부하에서 p95 300ms 이하 | 업로드·LLM·파일 전송 시간 제외, 오류율 별도 |
| SSE | 정상 서버의 저장 이벤트를 2초 이내 화면 반영 목표 | 네트워크 장애는 재연결·재생 성공으로 별도 판정 |
| 프런트 이벤트 | 활성 run 버퍼 기본 1,000건 | 과거 이력은 서버 페이징, 로그 유실 없이 탐색 가능 |
| 품질 회귀 | 승인·원문 추적·안전 제약 퇴행 0건 | 실패 입력을 성공으로 바꾸는 변경은 별도 근거 필요 |

첫 측정에서 목표가 부적절하면 측정 결과와 함께 ADR로 조정한다. 지연 개선을 위해 검토 단계나 필수 검증을 몰래 생략하지 않는다.

## 리팩터링 경계

`contracts`는 순수 모델과 검증, `application`은 사용 사례, `persistence`는 저장, `integrations`는 외부 I/O, `codegen`은 결정론 생성, `workers`는 장기 작업으로 나눈다. 한 번에 폴더를 모두 옮기지 않고 실제 변경하는 경로부터 적용한다.

정규화는 입력 해석·키 결정·관계 확장·물리명·최종 불변식 검사로 나누되 기존 public 함수는 어댑터로 유지한다. 고정 fixture의 `NormalizedModel`, SQL·Mermaid·RTM 바이트, Finding·model_hash를 비교한다. 정당한 출력 변경은 생성기 버전을 올려 이전 근거와 구분한다.

성능 캐시는 `pack_id + pack_version + common_version + policy_digest`로 키를 구성한다. 변경 가능한 경로 이름만으로 캐시하지 않는다. 최초 로딩 시 원본 해시 검증 후 불변 객체로 보관하며, 실행 중 정책 교체가 감지되면 기존처럼 중단한다. DB 연결·OAuth 토큰·고객 원문을 전역 캐시에 섞지 않는다.

## 스키마와 운영 개선

플랫폼 migration은 신규 빈 DB 초기화와 기존 `schema.sql` 기반 DB의 baseline 등록을 나눈다. 기존 표가 실제 기준 구조인지 검사한 뒤 baseline을 기록하고, 무조건 최신 버전으로 stamp하지 않는다. checkpointer 표는 라이브러리 소유로 구분한다. 실행 중인 프로세스와 동시에 destructive DDL을 수행하지 않는다.

migration 도구로 Alembic을 도입하되 현재 psycopg 저장 계층을 ORM으로 모두 바꿀 필요는 없다. 수동 SQL migration도 버전 관리한다. 자동 비교가 만든 이전안은 후보이며 컬럼 rename·데이터 변환은 명시적으로 검토한다. [Alembic 공식 설명](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)

지표는 run/job별 단계 시간·큐 대기·재시도·lease 상실·DB 풀 대기·LLM 토큰·실패 코드·테스트 통과/실패/미실행을 기록한다. 원문·메일 본문·키·SQL 데이터 행은 로그에 넣지 않는다. `/health`와 DB·작업자 readiness를 분리하고 백업 복구를 실제 사본에서 확인한다.

## 완료 산출물

각 개선 작업은 변경 코드, 필요 회귀 검사, 기준선과 비교 결과, 호환성·복구 설명을 제공한다. 패키지 업그레이드는 잠금 파일과 관련 회귀를 같은 변경으로 다루며 불필요한 일괄 최신화는 하지 않는다.

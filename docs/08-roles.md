# 개인 개발 운영과 모듈 경계

> 상태: 적용. 개인 개발자가 전체 저장소를 유지하며 변경 영향과 검증 근거를 기록한다.

## 모듈 책임

| 모듈 | 책임 | 주요 경로 |
|---|---|---|
| 실행 제어 | 그래프·중단과 재개·재작업·호출 한도 | `specton/graph.py`, `specton/runner.py`, `specton/llm/` |
| 입력과 지식 | 문서 추출·원문 위치·도메인 팩 | `specton/ingest/`, `specton/packs/`, `domain_packs/` |
| 계약과 저장 | 타입·API·스냅샷·승인·파일 메타데이터 | `specton/contracts/`, `specton/api/`, `specton/persistence/` |
| 생성과 검증 | 모델 정리·DDL·ERD·RTM·규칙·격리 DB | `specton/codegen/`, `specton/review/`, `specton/validate/` |
| 출력과 화면 | 문서 렌더링·실행 UI·배포 구성 | `specton/export/`, `frontend/`, `docker/` |
| 평가 | 고정 조건·정답 대응·분모·실패 집계 | `specton/evaluation/`, `tests/`, `docs/evidence/` |

## 작업 순서

요구사항·계약 → 작은 수직 구현 → 오류·재시작 검증 → 문서 갱신 → 릴리스 확인 순서로 진행한다. 공통 계약을 바꾸면 파서·노드·저장·API·프런트 타입·테스트의 영향을 먼저 찾는다.

확장 실행 순서는 [개발 계획](planning/README.md)에 있다. 기존 문서 생성 기능과 새 업무 시스템 생성 기능은 완료 기준을 구분한다.

## 변경 기록

변경마다 목적, 영향받는 요구사항, 수정 경로, 실행한 검사, 남은 제약을 남긴다. 원격 이슈·PR은 선택적 기록 수단이며 이전 저장소의 보드나 계정에 의존하지 않는다.

## 평가 독립성

개발용 입력과 인수용 입력을 분리하고 평가 전에 팩·프롬프트·정답 해시를 고정한다. 같은 개발자가 이미 본 자료로 수행한 실험은 회귀 또는 탐색 평가로 표시한다. 개인 검토를 독립된 다른 사람의 검토로 표현하지 않는다. 평가 도구의 기존 승인 JSON 형식은 호환성을 유지하며, 역할명 일반화는 별도 계약 이전 작업으로 계획한다.

## 완료 기준

범위 충족, 필요한 검사 통과, 오류·미실행 상태 기록, 문서 갱신, 변경 diff 확인을 완료해야 한다. 문서 작성만으로 기능 구현이나 운영 배포가 완료됐다고 표시하지 않는다.

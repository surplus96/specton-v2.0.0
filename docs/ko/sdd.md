# 승인 설계에서 실행 가능한 앱까지

[![한국어](../assets/lang-ko.svg)](../ko/sdd.md) [![English](../assets/lang-en.svg)](../en/sdd.md)

## 입력과 생성 범위

SDD는 Spec-Driven Development다. Specton은 승인된 기능 명세·ERD·DDL·RTM과 설계 상태를 프로젝트 기준으로 연결하고 실행 명세를 작성한다. 화면·역할·API·저장 매핑·업무 조건·인수 기대값은 설계 초안만으로 확정할 수 없으므로 검토·승인해야 한다.

기본 경로는 **도메인 독립 계약 컴파일**이다. 설계의 테이블·키·관계를 읽고 해당 도메인의 앱을 만든다. 주문·반품·설비 테이블을 고정으로 넣지 않는다. 과거 기준정보·재고·상거래 템플릿과 `templates/legacy/`는 기존 승인 패키지 호환성 때문에 보존한다.

| 계약 | 지원 내용 |
|---|---|
| 레코드 작업 | 등록·조회·수정, 복합 키·관계 매핑, 명시적 상태 전이 |
| 필드 불변 조건 | 타입이 있는 비교와 all/any, 변경 후 값 검증 |
| 다중 레코드 명령 | 선언된 잠금 대상, 조건·계산·쓰기·반환, 단일 트랜잭션 |
| 계산·집계 | Decimal 정밀도·반올림·단위·빈 결과·0 나눗셈 정책, 선언된 필터·상한 |
| 기본 UI | 계약 기반 폼·목록·행 수정·검색·페이지 이동·관계 선택, 로딩·오류 안내 |
| 고객 인증 | 별도 고객 계정·세션과 API별 역할 검사 |
| 인수 사례 | 실제 API 입력·기대 응답·요구 추적, 정상·경계·실패 사례 |

지원 범위를 넘는 일정 실행, 외부 시스템 동작, 행별 소유권, 구조 변경 데이터 이전, 완성형 시각 디자인은 [구현 범위와 제약](roadmap.md)에 명시한다. 팩 승인이나 문장 진단만으로 실행 가능성을 판정하지 않는다.

## 구조 도출과 업무 구현의 구분

현재 입력 경로는 플랫폼에서 실제 승인된 설계의 스냅샷과 네 산출물이다. 임의의 외부 설계 파일 네 개만 업로드해 승인 근거 없이 앱을 생성하는 경로는 제공하지 않는다.

`derive`는 정리된 테이블·키·관계를 읽어 등록·조회·수정 API, 화면, 저장 매핑을 제안한다. 요구 연결은 `needs_review`로 남으며 업무 규칙·실행 인수 기대값은 별도 검토한다. 명령·계산이 이미 있는 명세는 구조 도출로 덮어쓰지 않고 기존 계약을 보완한다.

명령·계산의 모델과 지원 연산은 [업무 실행 계약](business-contracts.md), 전체 사용자 순서는 [처리 흐름](workflow.md)을 따른다.

## 실행 명세

타입의 기준은 [SpecBundle](../../specton/contracts/specification.py)이다. 현재 확장은 `spec-v0.9`, 생성기는 `executable-design-v11` 계약을 포함한다. 이는 패키지/명세 형식 버전이며 프로젝트의 명세 개정 번호와 다르다.

- `baseline`: 실제 승인 설계의 모델·산출물·프로젝트 기준.
- `requirements`: 포함·유예 범위와 근거. 미지원 요구를 지우지 않는다.
- `roles`, `use_cases`, `apis`, `screens`: 호출 권한, 사용 흐름, 입출력과 화면 연결.
- `entities`, `storage_bindings`, `domain`, `invariants`: 실제 저장 구조·작업·명령·계산과 조건.
- `questions`: 승인 전에 해결할 불확실성.
- `acceptance_cases`: 요구별 자연어 또는 실행 가능한 사례. 자연어 사례는 실행 근거가 생기기 전 `not_run`이다.

검토 준비 파일의 안정 ID·출처·가정·인수 기대값은 사용자가 확인한다. `scripts/validate_test_preparation.py`는 저장된 명세·설계와 준비 파일을 오프라인 검사하며 승인이나 앱 실행을 대신하지 않는다.

## 사용자 흐름

1. 프로젝트에 최종 승인 실행을 연결하고 **실행 명세 검토**를 연다.
2. 승인 설계에서 초안을 만들고 요구별 포함/유예 이유, API·화면·저장 구조를 확인한다.
3. 필요하면 외부 전송에 동의한 뒤 AI 보완을 요청한다. 제안을 검토하고 저장한다.
4. 업무 규칙과 정상·경계·실패 인수 기대값을 보완한다. 준비도 점검의 미해결 항목을 확인한다.
5. 최신 명세 버전과 해시를 확인해 승인한다. **승인한 명세로 소스 생성·조회**를 실행한다.
6. **격리 검증 요청·재실행**으로 해당 소스의 API·브라우저 결과를 확인한다.
7. **브라우저 검증 소스로 미리보기 준비 → 미리보기 열기**로 실제 화면을 시험한다.
8. **검증 후보 비교·채택**에서 기준 후보와 변경·설계 일치·미검증 항목을 검토하고 채택한다.

## AI 보완의 경계

AI 결과는 제안이다. 작은 명세의 보완도 서버 계약 검사와 사용자 승인을 거친다. 대형 기존 실행 계약은 전체 JSON을 다시 생성하는 대신 제한된 기존 화면·설명 변경과 미해결 질문을 병합한다. 실행 계약·인수 기대값은 서버에 보존하며 이 경로에서 새 API·명령·계산을 자동 확정하지 않는다. 보호 필드 변경과 알 수 없는 대상은 거절한다.

## 원자성·재시도·정밀도

명령은 선언된 행과 조건을 확인한 뒤 하나의 DB 거래에서 처리한다. 중간 실패는 전체 쓰기와 요청 기록을 롤백한다. 성공한 같은 요청 키는 저장된 결과를 반환하고, 실패 후에는 수정한 입력으로 재시도할 수 있다. 실제 지원 잠금·키·쓰기 구조는 계약 컴파일러가 검사한다.

수량·금액·계산은 부동소수점 추정 대신 명시적인 Decimal 정책을 사용한다. 단위·스케일·반올림·필터·최대 조회 행 수와 빈 결과 정책이 불명확하면 별도 계약 검토가 필요하다. 임의 Python·JavaScript·SQL을 명세에 삽입해 실행하지 않는다.

## 소스·설계·검증의 일치

소스 ZIP에는 승인 명세, 원본 설계, `design/revised/`의 재생성 문서, 백엔드·프런트 계약, 파일 manifest, 설치·운영 도구가 들어간다. 검증기는 승인 명세에서 다시 컴파일한 계약과 문서 바이트를 비교한다. 문서 해시만 다시 쓴 변조 패키지도 거절한다.

화면·정책 변경에서 저장 구조가 같으면 ERD·DDL이 같은 것이 정상이다. 원본 승인 설계는 이력으로 남고 변경 설계는 새 명세 버전에 연결된다. 검증 통과, 후보 채택, 운영 서비스 배포, 고객 업무 전체 인수는 서로 다른 상태다.

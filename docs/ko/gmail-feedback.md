# Google 로그인과 Gmail 변경 요청

[![한국어](../assets/lang-ko.svg)](../ko/gmail-feedback.md) [![English](../assets/lang-en.svg)](../en/gmail-feedback.md)

## OAuth 설정

Google 로그인은 플랫폼 사용자·프로젝트 소유권을 식별한다. Gmail은 별도 읽기 권한을 요청한다. 두 기능은 같은 OAuth 웹 클라이언트를 사용하되 **두 콜백을 모두 등록**한다.

| Google Cloud 항목 | 로컬 값 |
|---|---|
| 승인된 JavaScript 원본 | `http://localhost:5173` |
| 로그인 리디렉션 URI | `http://localhost:5173/api/v1/auth/google/callback` |
| Gmail 리디렉션 URI | `http://localhost:5173/api/v1/integrations/gmail/callback` |

JavaScript 원본에는 경로나 끝 `/`를 넣지 않는다. Gmail 콜백이 기존 로그인 콜백을 대체하지 않는다. OAuth 동의 화면과 테스트 사용자를 설정하고 Gmail API를 활성화한다. 실제 배포 origin은 HTTPS 도메인으로 바꾸고 콜백도 함께 맞춘다.

`.env.example`을 기준으로 `SPECTON_PUBLIC_ORIGIN`, `SPECTON_GOOGLE_CLIENT_ID`, `SPECTON_GOOGLE_CLIENT_SECRET`을 설정한다. Gmail 토큰 암호화 키는 한 번 생성하고 비밀 설정에 보관한다.

```bash
uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

생성 값을 `SPECTON_GMAIL_TOKEN_KEY`에 넣는다. 이 키는 재시작 후에도 유지해야 하며 바꾸면 기존 연결을 다시 설정해야 한다. AI 분석을 사용할 때만 `SPECTON_FEEDBACK_ANALYSIS_ENABLED=true`로 설정한다. 일일 분석 한도는 별도 설정하며, 요청별 전송 동의도 필요하다.

## 연결·수집 확인

1. Google 로그인 후 **고객 메일 → Gmail 연결**에서 읽기 권한을 승인한다.
2. 검색 조건에 테스트 범위를 입력한다. 예: `subject:Specton-demo newer_than:7d -in:drafts`.
3. **수집 범위 저장**을 누른다. 주기적 수집 여부를 선택한다.
4. 연결된 Gmail 주소로 합성 변경 요청을 보내고 **지금 동기화**를 누른다.
5. 작업 상태가 완료되면 **수신함 새로고침**으로 제목·발신자·본문을 확인한다.
6. 다시 동기화해 같은 Gmail 메시지가 중복되지 않는지 확인한다.

검색식은 앱의 수집 필터이며 Google 권한을 특정 메일로 한정하지 않는다. 연결·sync 완료만으로 메일이 존재한다는 뜻은 아니다. 목록이 비면 Gmail에서 같은 검색식의 실제 결과와 스팸·휴지통 여부를 먼저 확인한다. 메일 발송·삭제·읽음 처리는 수행하지 않는다. 수집과 분석은 별도 작업이다.

## 승인된 변경 반영

대상 프로젝트에는 승인 명세와 채택된 구현 기준이 있어야 한다.

1. 수집한 메일을 열고 프로젝트를 선택한다. 본문의 요청을 그대로 인용해 변경 요청을 등록한다.
2. 외부 AI 전송 범위에 동의한 뒤 **에이전트 영향 분석**을 요청한다.
3. 요약·직접 영향·연관 대상·미지원 항목·질문을 확인한다. 필요한 답변을 저장하면 이전 승인 근거가 무효화되므로 다시 분석·검토한다.
4. 기존 값과 제안을 비교하고 **검토한 변경안 저장**을 누른다.
5. 검토 사유와 확인을 입력해 **변경안·실행 명세 승인**을 실행한다.
6. **승인 변경으로 후보 생성·검증 요청**을 실행한다. 이 단계에서 새 명세 버전과 후보를 만들고 검증을 요청한다.
7. 자동 검증과 격리 화면을 확인한 뒤 **기존 후보와 비교·채택**으로 이동한다.
8. 명세·설계·소스 일치, 변경 파일과 미검증 업무를 검토하고 채택한다. 변경 요청의 **반영 완료**와 이력을 확인한다.

변경안 승인과 구현 후보 생성은 구별된다. 생성/검증 등록 실패 시 새 명세·소스 DB 거래를 롤백하고 승인된 변경안으로 재시도한다. 중복 요청과 오래된 기준·해시를 검사한다.

## 허용된 계약 변경

기존 화면 이름·문구, 허용된 권한·요구 필드, 기존 명령·계산의 제한된 정책 변경을 지원한다. 새 테이블·API·입력·잠금 대상·쓰기 구조를 자동 추가하는 경로는 아니다.

명령·계산 정책이 바뀌면 **모든 실행 인수 사례**의 기대값을 사람이 검토한다. AI는 기대값을 바꾸지 않는다. 성공 응답의 허용된 기대값 변경은 단계별 근거와 함께 저장하며, 실패 검사·입력·권한·사례 연결을 지우거나 통과로 완화할 수 없다. 실제 재검증이 실패하면 채택 근거가 생기지 않는다.

## 변경 산출물과 검증 근거

| 대상 | 변경 반영 방식 |
|---|---|
| 승인 원본 | 기존 설계와 명세 이력 보존 |
| 실행 명세 | 검토한 변경과 승인 근거를 새 버전에 연결 |
| 설계 문서 | 기능·ERD·DDL·RTM 및 실행 명세 사본을 `design/revised/`에 생성 |
| 구현 소스 | 새 명세에서 백엔드·프런트 계약을 재컴파일 |
| 검증 결과 | 새 소스 해시에서 설계 일치·API·브라우저 검사 수행 |
| 구현 기준 | 비교·채택 성공 시 변경 요청을 반영 완료로 전환 |

화면명이나 계산 정책만 바뀌어 저장 구조가 같으면 ERD·DDL의 내용이 유지될 수 있다. 지원하는 명령·계산 수정 항목과 기대값 검토 규칙은 [업무 실행 계약](business-contracts.md)을 따른다. 동일 구조의 데이터 이전·실패 복구 검사는 [납품 가이드](deployment.md)의 별도 절차이며 Gmail 후보 채택이 운영 데이터 이전을 실행하지는 않는다.

## 상태와 운영

대표 흐름은 `received → analysing → needs_input / awaiting_decision → approved → validating → reviewable → applied`다. 실제 상태·전이 조건은 [feedback API](../../specton/api/feedback.py)를 따른다. 분석 실패·검증 실패는 정상 완료와 구분하며 UI에서 새로고침·재시도를 지원한다.

토큰은 암호화해 저장한다. Gmail 연결을 끊으면 수집을 중단한다. OAuth 상태, 갱신 토큰, 일일 분석 한도, 작업 lease는 [통합 코드](../../specton/integrations/)와 [작업자](../../specton/feedback/worker.py)에서 관리한다. 메일의 지시는 분석 대상이며 도구 실행이나 데이터 외부 전송 권한을 자동으로 부여하지 않는다.
